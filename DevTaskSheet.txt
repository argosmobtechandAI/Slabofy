BE-01
OTP Send
POST /api/auth/send-otp
Accepts: { phone }
Generate 6-digit OTP, store in Redis with key otp:{phone} and TTL 10 mins
Send via MSG91 or Twilio SMS API
Return: { message: 'OTP sent' }
P1
Rate-limit: max 3 requests per phone per 10 mins
BE-02
OTP Verify + JWT Issue
POST /api/auth/verify-otp
Accepts: { phone, otp }
Verify OTP from Redis — delete after successful match
If user exists: return JWT. If new user: create user record first, then return JWT
JWT payload: { userId, role, phone } — expiry 7 days
Return: { token, user: { id, name, phone, role } }
P1
JWT secret must be in .env — never hardcode
BE-03
Auth Middleware
Middleware: verifyToken(req, res, next)
Extract Bearer token from Authorization header
Verify JWT, attach decoded user to req.user
Return 401 if missing/invalid/expired
Middleware: requireRole(role) — returns 403 if req.user.role !== role
P1
All protected routes must use verifyToken. Admin routes must also use requireRole('admin')
BE-04
User Profile

Phase 3 — Backend: Group Buying Engine
Most complex backend module — build carefully
WARNING: This is the most business-critical backend module. The group engine must handle concurrent joins, timer expiry, payment pre-authorization, and state transitions atomically. Use database transactions everywhere in this module.
Task ID
Task / Module
What to Build
Priority
Notes / Dependencies
BE-12
Create Group
POST /api/groups/create
Accepts: { product_id, target_size } — target_size must be one of [2,3,5,10]
Validate product is active and not out of stock
Insert into groups: status='active', timer_end = NOW() + 24h
Add creator as first group_member
Set current_size = 1
Store timer in Redis: SET group:{id}:timer {unix_timestamp} EX 86400
Generate shareable invite URL: /join/{group_id}
Return: { group_id, invite_url, timer_end, tier_price }
P1
creator is automatically joined — do not make them re-join
BE-13
Join Group
POST /api/groups/:id/join
Check: group status must be 'active'
Check: timer_end must be in the future (check both DB and Redis)
Check: user not already in group — UNIQUE constraint on group_members
Check: current_size < target_size
Insert into group_members
Increment groups.current_size by 1 (use atomic UPDATE SET current_size = current_size + 1)
If current_size === target_size: trigger Group Completion flow (see BE-14)
Else: send WhatsApp notification to group creator (new member joined)
Update Redis member count cache
P1
CRITICAL: Use a DB transaction wrapping the size increment + completion trigger to prevent race conditions
BE-14
Group Completion Flow
Triggered internally when current_size === target_size
Set groups.status = 'complete'
Capture payment pre-authorization for ALL members simultaneously
Create orders for all members with status='confirmed'
Send WhatsApp blast to all members: 'Your group is complete! Order confirmed.'
Send push notification to all members
Do NOT expose this as a public API — it is called internally from BE-13
P1
Payment capture must be in a try-catch — if capture fails for any member, log error and flag for manual admin review
BE-15
Group Status / Real-Time Poll
GET /api/groups/:id/status
Return: { current_size, target_size, status, timer_remaining_seconds, members_count, tier_price }
timer_remaining_seconds: fetch from Redis, fall back to DB timer_end - NOW() if Redis key missing
Frontend will poll this every 5-10 seconds for live updates
P1
This endpoint will be hit frequently — keep it lightweight, read from Redis cache where possible
BE-16
Extend Timer
POST /api/groups/:id/extend-timer
Only group creator can call this (verify req.user.id === groups.creator_id)
Check: extension_used must be false
Extend timer_end by configurable duration (default: +12 hours)
Set extension_used = true
Update Redis TTL: EXPIRE group:{id}:timer {new_seconds}
Send WhatsApp notification to all current group members
P2
Extension duration should be configurable from admin settings, not hardcoded
BE-17
Cancel Group
POST /api/groups/:id/cancel
Only creator can cancel — verify ownership
Only possible when status = 'active'
Set status = 'cancelled'
Void all payment pre-authorizations for all members
Send WhatsApp notification to all members: 'Group cancelled, payment hold released'
Delete Redis timer key
P1
Payment void must happen before status update — if void fails, do not mark as cancelled
BE-18
Group Expiry Cron Job
Scheduled job: runs every 5 minutes
Query: SELECT * FROM groups WHERE status='active' AND timer_end < NOW()
For each expired group:
  Set status = 'expired'
  Void all payment pre-authorizations
  Send push notification to all members
  Delete Redis timer key
Use node-cron or a dedicated worker process
Log every expiry action in notification_log
P1
This cron is critical — without it, expired groups will never close. Test thoroughly with short timers in dev
BE-19
Admin: Manual Group Completion
POST /api/admin/groups/:id/force-complete
Admin can override an expired or stalled group and mark it complete
Capture payment for all existing members regardless of target size
Set status = 'complete'
Log admin action with admin_id and timestamp in audit trail
P2
Audit log is mandatory — admin overrides must be traceable

Create Payment Order (Pre-Auth)
POST /api/payments/create-order
Accepts: { group_id }
Calculate amount from product_tiers based on group's target_size
Call Razorpay Orders API: create order with payment_capture = 0 (pre-auth mode)
Store razorpay_order_id in payment_preauth table with status='authorized'

P1

BE-21
Capture Payment (on Group Complete)
Internal function: capturePayment(razorpay_order_id, amount)
Calls Razorpay Capture API
On success: update payment_preauth.status = 'captured', set captured_at
Update order.status = 'confirmed'
On failure: log error, flag order for admin review
P1
Called from Group Completion Flow (BE-14), never directly by user
BE-22
Void Payment Authorization
Internal function: voidPayment(razorpay_order_id)
Calls Razorpay void/refund API
On success: update payment_preauth.status = 'voided', set voided_at
On failure: log and alert admin — do not silently fail
P1
Called from Group Cancel (BE-17) and Expiry Cron (BE-18)
BE-23
Razorpay Webhook Handler
POST /api/webhooks/razorpay
Verify webhook signature using Razorpay webhook secret
Handle events: payment.authorized, payment.captured, payment.failed, refund.created
Update order and payment_preauth records based on webhook event
This is the source of truth — keep DB in sync with Razorpay
P1
Webhook endpoint must be public (no JWT auth). Verify signature before processing — never trust raw webhook data
BE-24
COD Order Flow
POST /api/orders/cod
For Cash on Delivery: skip pre-auth flow entirely
Validate pincode against allowed COD pincodes list (store in DB or config file)
Create order directly with status='confirmed', no payment_preauth record
COD orders count toward group completion the same as paid orders
P2
COD pincodes list must be manageable from admin panel
